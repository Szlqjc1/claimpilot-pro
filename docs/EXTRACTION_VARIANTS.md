# Extraction variants: labels and layout

**Question.** Does extraction still work when the invoice is not our template? The seed renders every invoice
the same way, so the hero results say nothing about a supplier who writes `Inv. #`, `Rechnungsnummer` or `发票号`,
or who puts the value under its label instead of beside it.

**Answer, in one paragraph.** Layout broke nothing: all three layouts scored 100 % field accuracy, 0 % escalation
and 0 % error in cleared claims. Labels didn't break the model either: it mapped all five label styles to the right
fields, German and Chinese included. **What broke first was not a label alias but what a long label does to the page,
and what OCR does to a digit:**
- **Verbose labels widened the header**, and the vendor name wrapped onto two lines. OCR kept only the first line
  ("Buckeye Fastener" for *Buckeye Fastener Supply*), the model returned that prefix, and grounding found it in the
  text. Two claims auto-cleared with a truncated vendor name; one more did the same in the Chinese variant.
- **On the abbreviated variant, OCR read PO `4501061` as `45010061`.** The model copied it faithfully, so the value is
  grounded and wrong, and the claim cleared.
- **Chinese labels** come out of the English-only OCR as noise (`HFHEHEA`, `ZIHAH`). The model still found every value
  from its shape, but page confidence dropped to 0.73–0.77, so R-14 escalated 2 of 20 correct documents.

The third column is the one that matters, and it is **not** zero on the label axis: 4 of 98 auto-cleared documents
carried a wrong field. All four are the class grounding cannot see by design (D-37): a value that is wrong but
present in the OCR text.

## Method

- **Documents:** 20 seeded claims that auto-clear on their reference extraction, evenly spaced by claim ID
  (procurement, MRO, services, prototype, travel). Starting from claims that would pass untouched makes column 3
  measure what a variant does to them.
- **Rendering:** `src/lib/bench/variants.ts` renders the same `InvoiceDoc` (identical values) as HTML in 5 label styles
  × the canonical layout, and 3 layouts × the canonical labels. That is 140 unique documents, since canonical ×
  label-left is shared, and 160 rows. Headless Chromium rasterises each at ≈ 300 dpi; no blur or noise, so only the
  axis varies.
- **OCR:** the app's own pipeline (`OCR_PIPELINE`: grayscale clean-up, PSM 3) and the real Tesseract with `eng`.
- **Extraction:** the live model through the app's own `extractWithDeepSeek` and prompt `extract-v2`. As for an upload,
  confidence comes from the OCR page, never the model.
- **Scoring:** grounding, presence (D-44) and the full 19-rule engine, with the claim's own SAP context
  (`seedRiskInput`).
- **Metrics, per variant:**
  1. **field accuracy:** of the critical values the model returned, how many match the reference, using the engine's
     own normalisation;
  2. **escalation rate:** documents where R-14 or R-19 fired;
  3. **error in cleared claims:** of the documents the engine auto-approved, how many carried a wrong or missing
     critical field.

  95 % bounds are exact binomial.

## What the benchmark changed in the app

The first run, with D-44 as committed in `aed93c5`, showed **10 % escalation on the canonical template**: every
travel invoice in the sample. Tesseract reads the label-left header column by column, so `PO Number` and its `—`
come out on different lines. Presence then classified the PO as `unreadable`, and D-44's new R-14 trigger escalated
a PO those claims do not need. Fixed in `453159a`, recorded in D-45:
- a label without a value fires R-14 only on a **required** field (an optional field never escalates);
- a standalone dash or N/A followed by whitespace counts as "none" (OCR flattens a table row: `PO Number: — Release: —`).

The tables above are after the fix, re-scored from the cached extractions with no new model calls.

## Limits

- **The renderer is ours.** The vendor-name wrap is real behaviour of this renderer under long labels. Real invoices
  wrap long names too, but the rate here measures our template, not the world.
- **Clean renders only.** Degradation is measured separately (`docs/GROUNDING_BENCH.md`); combining a degraded scan
  with a foreign label set is untested.
- **The OCR is English-only.** A Chinese invoice is read as noise plus Latin values. That the model still got every
  value says more about the values (Latin IDs, ISO dates, `$` amounts) than about Chinese support. A real Chinese
  invoice with Chinese vendor names would need `chi_sim`.
- **The label aliases have no German entries**, and Chinese labels don't survive `eng` OCR, so for those variants
  presence cannot tell `absent` from `unreadable`. It didn't matter here because every value was extracted.
- **20 documents per axis.** A 0 % row has a 95 % upper bound of about 14 %. These rows show where things break, not
  rates to quote.

## What would close column 3 (not implemented)

Both failure kinds are values that are in the text but disagree with SAP master data the claim already carries:
- the extracted vendor vs `Claim.vendorName` (normalised): this catches the truncated names;
- the extracted PO vs `Claim.poNumber`: this catches the OCR digit insertion.

A cross-check rule would have caught all 4. It is a new rule with points, i.e. a scoring change, so it is left for a
separate decision rather than added here.

## Reproduce

```bash
pnpm bench:variants
```

This needs `AI_MODE=live`, `DEEPSEEK_API_KEY` and `./eng.traineddata`. Without them it prints why and exits 0, so CI
stays green. OCR text and model output are cached under `.bench-cache/variants/`, keyed by HTML and by OCR text +
prompt version + model, so a re-run makes no model calls. Raw rows: [`docs/variants.csv`](variants.csv).

The full run made 133 model calls: 152,826 input and 71,255 output tokens. The config names `deepseek-chat`; the API
reported `deepseek-flash` as the serving model.
