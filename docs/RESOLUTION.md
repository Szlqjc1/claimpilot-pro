# Text size and scan resolution

**Question.** The font arm in D-48 concluded "8 pt is fine", but that was measured at ≈ 300 dpi, where 8 pt text is
large in pixels. What decides whether OCR can read a value is the character height **in pixels**. That depends on the
point size *and* the scan resolution, and it had never been swept.

**Method** (`scripts/resolution-sweep.ts`, `pnpm bench:resolution`; model-free):
- One A4 page at a fixed **200 dpi** (1654 × 2340 px), with the same layout, data and image size for every size.
- Only the text size changes. Every element is scaled from one body size (`sizeCss`), so the critical values (in the
  header and totals tables) shrink too.
- For each size, the x-height is **measured** in pixels on a rendered line of "x", not derived from the point size.
- The same 20 documents as every other benchmark. OCR is the app's own preparation (grayscale, illumination
  normalisation, 2× upscale, PSM 3) and the real Tesseract.

**Metrics, none from a model:**
- **CER** against the renderer's own transcript (order-insensitive, so Tesseract's column order doesn't count);
- **critical values found** by the grounding matchers;
- **R-14 / R-19** with the **known-good** extraction substituted for the model's: does the system notice it could not
  verify the page? R-19 cannot fire in that setup, because a known-good value is never "absent". The live run below
  covers it;
- **mean OCR confidence**, next to the CER, for calibration.

The specified range (6–14 pt) did not break, so it was **extended downward to 3–5 pt** to find the break point.
Those rows are marked "ext.".

## Where it breaks

**Between an x-height of 7 px and 6 px.**
- At **7 px** (5 pt at 200 dpi) every critical value on all 20 documents is still found, at 11.4 % CER.
- At **6 px** (4 pt) only 47 % are found and CER jumps to 45 %.
- At **4 px** (3 pt) 18 % are found, at 85 % CER.

From 9 px up (6 pt and above) CER sits at 2–5 % and nothing is lost. Measured at the OCR **input**, i.e. before the
clean-up's 2× upscale, which is a large part of why small text survives as well as it does.

**In practice:** below ≈ 7 px x-height (8 pt text scanned at ≈ 125 dpi or less) the five fields stop being verifiable.
That is a sharp 12-megapixel phone photo of an A4 page taken from farther than about 0.6 m, with the page filling about
a quarter of the frame width. Motion blur or a soft lens brings that distance in.

**The safety claim holds.** At both failing sizes, R-14 fired on 20/20 documents with the known-good extraction, and
none auto-cleared. The live run at 4 pt confirms the full pipeline:
- 20/20 went to review and 0 auto-approved;
- the model mostly **invented** values rather than returning nulls (38 wrong fields against 4 null), so the catches
  came from **R-14** (value not in the OCR text, 20/20) and **R-20** (value disagrees with the claim, 17/20), with
  **R-19** (required field absent) on 3.

**Calibration.** On this axis confidence tracks the damage: 0.93 at 2 % CER, 0.82 at 11 %, 0.55 at 45 %, 0.35 at 85 %.
That contrasts with the shadow failure (D-52), where a third of the page was missing at 0.92 confidence. Page
confidence falls when *every* glyph is hard to read, and says nothing when a *region* is lost. That is why the rules
check the values, not the confidence.

**Large type has its own failure, and it is layout, not resolution.** At 14 pt (20 px), CER rises to 6.4 % and one
document escalates. In this fixed-width layout, long values wrap onto two lines (`$48,` / `776.43`), and a split value
can't be matched. It is still caught (R-14), not cleared.

**Limits.** Clean renders in one sans face. Blur, noise and JPEG at low resolution compound with size and were not
crossed here. The phone-distance figure is geometry (field of view and pixel count), not a measured phone photo.
