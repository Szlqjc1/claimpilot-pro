# Decisions log

Decisions made where the build spec was ambiguous, contradictory, or impossible as written.

| # | Topic | Decision | Why |
|---|---|---|---|
| D-01 | R-04 near-limit band vs. CLM-2026-0148 | The 80–100% "near limit" advisory (Medium, 20 pts) applies **only when no PO covers the claim**. | $128,400 is 85.6% of the $150,000 Tooling limit. Applied literally, R-04 would add 20 points and CLM-0148 would score 85 instead of the spec's 65. The PO is the spend control for PO-backed categories (R-07 covers it), so the per-claim limit only acts as an early warning for non-PO spend. Limits and hero expectations are left exactly as specified. |
| D-02 | Exception Rate formula | `claims with ≥1 exception raised (Open, Resolved or Waived) ÷ analyzed/posted claims`. The card subtitle shows the count of claims with **open** exceptions. | Posted claims have resolved exceptions. Counting only open ones could not reach the spec's 25–40% target alongside 70% Posted. With this definition, Auto-Clear + Exception Rate = 100%, which matches the target ranges (55–70% / 25–40%). |
| D-03 | Extraction schema additions | Added three nullable fields: `projectCode` (R-01/R-02), `remitTo {bankName, accountLast4}` (R-17), `attendees {count, names}` (R-12). | The rules in Section 8 need this data and the Section 7.4 schema has nowhere to carry it. Remit-to bank details are the vendor's last 4 digits only; no employee banking data is extracted. |
| D-04 | Historical POs | The 12 named SAP POs are seeded as "open POs" (shown on /policies). Each historical claim gets its own generated PO in the `4501xxx` series, closed after posting. | 120 historical claims across 8 projects and 15 vendors can't share 12 POs without tripping R-02/R-07 everywhere. |
| D-05 | Dashboard period anchor | Periods are anchored to the latest claim's submission date ("data as of"), not the wall clock. | The demo dataset stays meaningful whenever it is opened, so "Last 12 months" doesn't go empty after a few weeks. |
| D-06 | Deterministic "as of" for vendor and date rules | R-06 (W-9/insurance expiry) and R-13 ("future" invoice date) are evaluated against the claim's `submittedAt`, not `now()`. | Scores are reproducible and auditable regardless of when the audit runs. |
| D-07 | Prisma Decimal + SQLite | Money is stored as Prisma `Decimal`. All arithmetic converts to integer cents at the boundary (`toCents`). KPI sums run in JS over cents rather than SQL `SUM`. | SQLite stores DECIMAL with NUMERIC affinity. Doing the math in cents avoids float drift and stays portable to PostgreSQL. Covered by unit tests (round trip + `0.1 + 0.2`). |
| D-08 | `db:reset` script | `prisma migrate reset --force --skip-seed && prisma db seed` (`--skip-seed` stops the seed from running twice). The seed itself wipes and reloads the tables, so `pnpm db:seed` on its own also resets the demo. | Prisma 6 runs the seed automatically after reset. |
| D-09 | Fonts offline | Inter is self-hosted from `@fontsource-variable/inter` via `next/font/local`. | `next/font/google` needs internet at build time, which breaks the offline-demo requirement. |
| D-10 | shadcn/ui | Hand-written shadcn-style primitives (cva + tailwind-merge + Radix Dialog/Tooltip) instead of running the shadcn CLI. | The CLI needs network access and interactive prompts. The result is the same component pattern without a generator dependency. |
| D-11 | Lint script | `eslint .` with the flat config extending `next/core-web-vitals` + `next/typescript`. | `next lint` is deprecated in Next 15.5. Same rules. |
| D-12 | Playwright | Not installed. The golden path is covered by `src/tests/audit.test.ts` (integration against a real SQLite DB) and was run manually in a browser. | The spec allows a scripted API integration test when a browser install isn't practical. This keeps `pnpm install` offline-friendly. |
| D-13 | Uploads in mock mode | `/claims/new` accepts and stores PNG/JPEG/PDF, but running the audit on an upload in mock mode returns 422: "Live OCR is disabled in demo mode. Seeded claims use deterministic fixtures." | The spec forbids fabricating an extraction for an arbitrary upload. |
| D-14 | Vendor concentration watchlist rule | Evaluated only for categories with ≥2 active vendors. | Most demo categories have a single vendor, which would make ">35% of category spend" trivially true and crowd out useful callouts. |
| D-15 | Routing in flagged audit details | Routed by department: Plant Operations → Plant Controller, Supplier Quality → Supplier Quality Manager, R&D Engineering → R&D Finance Partner, Supply Chain → Supply Chain Controller. | Matches the spec's CLM-0144 example ("Routed to Plant Controller"). |
| D-16 | `Posted` visibility | The AI blocks render only for `Status === "Analyzed"`, exactly as specified. In production they should also render for `Posted` (see README). | Spec section 2.6. |
| D-17 | pnpm build scripts | `pnpm-workspace.yaml` → `allowBuilds` approves Prisma, esbuild and unrs-resolver. tesseract.js does not need its postinstall script. | pnpm 10+ blocks dependency build scripts by default. |
| D-18 | `.env` bootstrapping | `postinstall` copies `.env.example` → `.env` when `.env` is missing. | So `pnpm install && pnpm db:reset && pnpm dev` works from a clean clone with no manual step. |
| D-19 | AI panels after posting | `showAi` is now `claim.status !== "Pending"`: AI Structured Data and the AI-Annotated Invoice render for both `Analyzed` and `Posted` claims, and are still absent from the DOM while `Pending`. Supersedes D-16. | Once a claim can be posted (G-03), hiding the extraction and annotated invoice at that point would remove the evidence an auditor needs to explain why the invoice was paid. |
| D-20 | `postedAt` / `miroDocNo` as columns | Added nullable `postedAt DateTime?` and `miroDocNo String?` to `Claims` (migration `add_posting_fields`). The seed fills them for historical Posted claims (deterministic `MIRO-yyyyMMdd-<receipt-hash>`). Live posts use 6 random hex chars. | Posting state is queried and shown on the claim page, and it belongs to the claim record, not to a log line. Parsing it back out of the append-only AuditLog would be brittle. |
| D-21 | `instrumentation.ts` location | The hook lives at `src/instrumentation.ts`, not the repo root as the G-31 spec said. | With a `src/app` layout, Next.js 15 only loads `src/instrumentation.ts`. Verified: with the file at the root, `AI_MODE=Live pnpm dev` ran for 90 s in mock mode. With it in `src/`, the server prints `[env] Invalid configuration — AI_MODE: … received 'Live'` and stops. |
| D-22 | Env validation layering | `src/lib/env.ts` has two schemas. `envSchema` (types, enums, defaults) is used by `readEnv()`, which `aiConfig()` calls on every read, so a typo throws instead of falling back to mock. `startupEnvSchema` adds the cross-field rule (live mode needs a key) and runs once in `validateEnv()` at server start. | The integration test that checks the graceful `503 AI provider is not configured` path changes `process.env` at runtime. Putting the startup-only rule in `aiConfig()` would replace that 503 with a thrown error. Note: `next dev`'s parent process returns status 0 after the worker calls `process.exit(1)`. The server still stops and the error line is printed. |
