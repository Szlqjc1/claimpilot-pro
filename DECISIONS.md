| D-25 | Simulated extraction confidence | **What:** `fieldConfidence` (and line-item `confidence`) on seeded extractions is a deterministic value, not a measurement. `stableConfidence()` in `src/lib/receipts/invoice.ts` takes the first byte of `sha256(claimId + ':' + field)` and maps it linearly into [0.93, 0.995]. The only exceptions are the deliberately seeded `lowOcr` samples, which override `total` (0.68) or `invoiceNumber` (0.71). Nothing behind these numbers was observed or measured. **Why it exists:** R-14 (Low OCR Confidence) has to be demonstrable in a fully offline demo with no OCR engine or model in the loop, and the UI needs plausible confidence chips and box colors. **Consequences:** the values are uncalibrated and have no discriminative power. Every seeded extraction is generated from the source document, so all fields are correct and there are no errors for the scores to rank: AUC is undefined (no negatives), i.e. no better than chance (0.5) at any threshold. The values must not be read as a probability of correctness, and R-14 only fires on the seeded `lowOcr` samples. **Correct design:** replace model-reported or simulated confidence with a *measured, bucketed field error rate* `P(error \| field, source, quality bucket)`, estimated from a labelled set of extractions (field = vendor/invoice #/date/PO/total…, source = fixture/Tesseract/LLM, quality bucket = e.g. OCR mean confidence or image-quality decile), and refreshed as reviewers correct fields. Review decisions are then driven by expected loss: send a field to human review when `p · L > c`, where `p` is that measured error probability, `L` the cost of the error getting through (e.g. a wrong total or PO on a large invoice), and `c` the cost of a review, instead of a fixed 0.75 cut-off. **Explicitly unchanged:** R-14's points and threshold in `src/lib/risk/rules.ts` were intentionally left as they are, because the seed assertions and the KPI target ranges (auto-clear rate, exception rate, high-risk exposure) depend on them. | The demo needs offline, deterministic confidence for R-14 and the UI; documenting what the numbers are prevents them being mistaken for a calibrated quality signal. |

| D-32 | Login throttling across spoofable client identity | `POST /api/auth/login` checks three buckets, in order, before the user lookup and before scrypt, all answering the same `429 RATE_LIMITED`: (1) `login:global`, 100/min for the process; (2) `login:ip:<ip>`, 5/min; (3) `login:acct:<email>`, 10/min, keyed on the submitted email (trimmed and lower-cased, as the lookup does) whether or not the account exists. The 401 `INVALID_CREDENTIALS` path is unchanged. A throttled request writes one `Sign-in Throttled` audit row (metadata `{ requestId, ip, bucket }`, never the password), at most once per bucket key per minute. `rateLimit()` now bounds its map: above 5,000 keys it sweeps buckets whose hits are all outside their window, then drops oldest-inserted keys down to 90% of the cap. **Deviations from the task text:** the task's test 1 and acceptance expect the 6th spoofed-IP attempt on one email to be 429, but the same task fixes the account limit at 10 so a stranger cannot lock out a real user; the limit wins, so attempts 1–10 are 401 and the 11th is 429. Test 5 asks for two accounts "from the same IP", but the 5/min IP bucket would refuse the second account regardless; the test proves account buckets are independent with A exhausted and B signing in from another address. | `X-Forwarded-For` is client-supplied: rotating it gave every guess a fresh bucket. The account bucket is the one an attacker cannot rotate without changing the target, and the global ceiling caps total damage (and the rate new keys can enter the map) even when both other keys are fresh. Keys now include attacker-chosen text, so an unbounded map would be a memory-exhaustion vector. In-memory buckets assume a single process; multi-node needs Redis (README limitations). |
| D-33 | Login limiter: trust boundary and residual DoS | Follow-up to D-32. **Trust boundary:** `X-Forwarded-For` is client-controlled (Next route handlers cannot see the socket address), so every IP-keyed bucket is advisory: it slows a naive client and nothing more. The account bucket (`login:acct:<email>`, 10/min) is the only key an attacker cannot rotate without changing the target, so it is what stops brute force. **Global bucket:** raised from 100 to 1000/min; it is a CPU backstop (each non-throttled attempt costs a DB lookup plus one scrypt), deliberately set far above real usage. At 100/min it was a DoS lever: 100 cheap requests with rotating IPs made every sign-in return 429 for the rest of the minute. **Residual risk:** an attacker can still fill the global bucket (now ~1000 requests/min) and block everyone's sign-in for the rest of that minute. That belongs to an edge proxy/WAF (real client IP, connection limits) in production, not to an in-process counter. **Eviction:** `rateLimit()` re-inserts a key on every hit, so the map is in recency order and eviction is least-recently-used; previously `Map.set` on an existing key kept its insertion slot and a long-lived, actively-hit bucket was evicted first, resetting its counter. Dropping a live bucket still forgets its count, so flooding distinct keys can only slow the throttle, not preserve or reset a chosen bucket. Bounding the map (5,000 keys) is what makes an attacker-chosen key space (submitted emails) safe. Account (10) and IP (5) limits and the shared 429 body are unchanged. | Throttling must stop guessing without turning into an easier way to lock everyone out, and its comments must describe what the code actually does. |
