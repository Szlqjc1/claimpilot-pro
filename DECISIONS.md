| D-25 | Simulated extraction confidence | **What:** `fieldConfidence` (and line-item `confidence`) on seeded extractions is a deterministic value, not a measurement. `stableConfidence()` in `src/lib/receipts/invoice.ts` takes the first byte of `sha256(claimId + ':' + field)` and maps it linearly into [0.93, 0.995]. The only exceptions are the deliberately seeded `lowOcr` samples, which override `total` (0.68) or `invoiceNumber` (0.71). Nothing behind these numbers was observed or measured. **Why it exists:** R-14 (Low OCR Confidence) has to be demonstrable in a fully offline demo with no OCR engine or model in the loop, and the UI needs plausible confidence chips and box colors. **Consequences:** the values are uncalibrated and have no discriminative power. Every seeded extraction is generated from the source document, so all fields are correct and there are no errors for the scores to rank: AUC is undefined (no negatives), i.e. no better than chance (0.5) at any threshold. The values must not be read as a probability of correctness, and R-14 only fires on the seeded `lowOcr` samples. **Correct design:** replace model-reported or simulated confidence with a *measured, bucketed field error rate* `P(error \| field, source, quality bucket)`, estimated from a labelled set of extractions (field = vendor/invoice #/date/PO/total…, source = fixture/Tesseract/LLM, quality bucket = e.g. OCR mean confidence or image-quality decile), and refreshed as reviewers correct fields. Review decisions are then driven by expected loss: send a field to human review when `p · L > c`, where `p` is that measured error probability, `L` the cost of the error getting through (e.g. a wrong total or PO on a large invoice), and `c` the cost of a review, instead of a fixed 0.75 cut-off. **Explicitly unchanged:** R-14's points and threshold in `src/lib/risk/rules.ts` were intentionally left as they are, because the seed assertions and the KPI target ranges (auto-clear rate, exception rate, high-risk exposure) depend on them. | The demo needs offline, deterministic confidence for R-14 and the UI; documenting what the numbers are prevents them being mistaken for a calibrated quality signal. |
| D-26 | Authentication design | Local email/password with DB-backed sessions. **Where the check happens:** `src/middleware.ts` (Edge, no Prisma) only redirects to `/login?next=…` when the `cp_session` cookie is missing on `/dashboard`, `/claims`, `/audit`, `/policies`, `/queue`. The `(app)` layout calls `requireUser()`, which validates the token against the `Session` table and deletes expired rows. Every non-auth API route also calls `requireUser({ api: true })` and answers `401 UNAUTHENTICATED`. Without that, a forged cookie would pass the middleware and reach the data APIs. **Credentials:** `scrypt` (Node built-in, keylen 64, 16-byte salt, `salt:hash` hex), compared with `timingSafeEqual`. Unknown emails are checked against a dummy hash so both failure cases cost the same and return the identical message. **Logout** reads the token from the raw `Cookie` header so the route works with a plain `Request` (and in tests). **Redirect safety:** `next` is accepted only as a same-site relative path. **Out of scope / unchanged:** `role` is stored and displayed but not enforced (no role matrix in this task), and disposition/posting audit actors stay "AP Shared Services" (`run-audit.ts` and `disposition.ts` untouched). `pnpm shots` now signs in as the demo admin before capturing. | Real password checks and revocable sessions without adding dependencies, while keeping Prisma out of the Edge runtime. |
| D-27 | Minimal role enforcement (segregation of duties) | One helper, `canReview(user)` in `src/lib/auth/session.ts` (true for `reviewer` and `admin`), and exactly three server-side checks, each answering `403 FORBIDDEN` with the standard error body: (1) `PATCH /api/claims/:id/exceptions/:exceptionId` requires `canReview`; (2) `POST /api/claims/:id/post` requires `canReview`; (3) both routes reject a user acting on a claim whose `employee` equals their own name (no self-approval). `POST /api/claims` stays open to any signed-in user, but the claimant is always the session user resolved through the `Employee` master, never a form field. Audit actors are the real user: the exception row (`resolvedBy`) and its `Exception Resolved/Waived` log entry, the `Exceptions Resolved` summary on posting, and `postedBy` in the metadata of the `Posted to SAP` row (whose actor stays `SAP S/4HANA Integration`). Seeded history keeps "AP Shared Services". Supersedes the "role not enforced" note in D-26. Deliberately **not** done: a permission matrix, per-department scoping, or restricting who may run the AI-RPA audit. The claim page hides Resolve/Waive and Post to SAP when a check would fail, but the server checks are the enforcement. `src/tests/api-auth.test.ts` fails if any route under `src/app/api` (except login/logout) stops calling `requireUser`. | Identity has to constrain who can approve money without growing into an RBAC system the demo doesn't need. |
